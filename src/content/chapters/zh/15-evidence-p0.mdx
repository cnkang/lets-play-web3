<p class="lead">「我有代码」和「我能证明链上运行的就是这份代码」是两回事；「测试全过」和「没有漏洞」也是两回事。</p>

## Phase-0 是什么

本轮文档核对使用了项目所有者提供的原始实验仓库。[公开的实验记录节选](https://github.com/cnkang/lets-play-web3/blob/main/docs/evidence/phase-0-notebook-excerpts.md)保留原文行号和源文件校验值，第 10.2–10.6 节的决策结果晚于早期计划。本章的测试结果来自原复核，本轮没有重新执行。本地记录与链上交易分别说明。

Phase-0 指基础实验与复核阶段，不是缺陷优先级。本章讲其中的**技术复核与收尾**，包括链上只读核对、源码与<Term id="storage-layout">存储布局</Term>审查、<Term id="foundry">Foundry</Term> 测试、<Term id="verification">源码公开验证</Term>的准备，最后列出决策 D-01 到 D-05。这是项目自己做的复核，<strong>不是第三方专业<Term id="audit">审计</Term>证书</strong>。

## 结论：PASS WITH FINDINGS

复核把发现按严重程度分为五级：Critical（严重）、High（高）、Medium（中）、Low（低）和 Info（信息项）。PASS WITH FINDINGS 的意思是「通过，但有发现」。记录的缺陷与限制仍需理解和处理，不能读成「没有漏洞」。

<T label="Phase-0 发现按严重程度汇总">

| 级别 | 数量 | 条目 |
| --- | ---: | --- |
| Critical | 0 | — |
| High | 0 | — |
| Medium | 1 | F-V3-001：`type(uint256).max` 授权溢出，没有无限授权 |
| Low | 3 | F-V3-002 粉尘截断（当前链上未触发）；F-V3-003 注入粉尘时可见之和可偏离；F-ALLOW-001 MBox-Burn 遗留授权（已由 D-01 撤销） |
| Info | 6 | 事件单位（历史日志是旧单位）；中心化升级权；未使用的 `onlyOwner`；V1/V2 源码无法按当前文件精确复现；npm audit（工具链）；公共 RPC 无 archive |

</T>

没有发现会导致当前测试资产被盗、被<Term id="mint">铸造</Term>或权限失控的 Critical / High 问题。

### 两个值得讲的小插曲

- **Fuzz 曾失败两次**，原因是**测试预言机**（测试里计算「期望结果」的代码）的断言顺序有问题。修好的是测试，**合约没有改**。这说明测试失败不一定是合约有 bug，也可能是测试本身写错了。
- **16 次 Handler 意外回退**：Invariant 测试中，Handler 是替你随机发起各种调用的辅助代码。`batchTransferFrom` 被调用 3,166 次，其中 16 次（约 0.5%）出现了 Handler 没有预料到的<Term id="revert">回退</Term>。整笔 Handler 调用回滚，不变量仍然成立。Phase-0 把它判断为**测试脚手架（预言机边界）的残留**，不是合约漏洞。更稳妥的做法是以后做一个最小复现，确认它属于预期约束。

<Callout type="warn" title="49/49 通过 ≠ 没有漏洞">

单元测试全部通过，审查仍然记录了 1 个 Medium、3 个 Low 和 6 个 Info。测试只能证明「想到的那些情况」没问题。

</Callout>

## 源码匹配：Sourcify 与 Etherscan

部署到链上的是<Term id="bytecode">字节码</Term>，不是源码。**源码验证**是用同样的编译参数重新编译你提交的源码。如果得到的字节码与链上一致，就公开源码并标记已验证。（怎样申请 Etherscan <Term id="api-key">API 密钥</Term>，见附录 B。）

### Sourcify：8 个地址全部匹配

<Term id="sourcify">Sourcify</Term> 有两种常见结果。**exact_match** 指完全匹配，连元数据都一致；元数据是编译器附在字节码末尾的说明信息。**match** 指字节码匹配，但元数据不完全一致。8 个地址里 **5 个 exact_match、3 个 match**，不能统称「全部完全匹配」。

为什么 V1、V2 只能 match？第 14 章为了 V3 改过 V1 的源码，而当时工作区**还没有 Git 历史**，取不回部署时的那一份。Phase-0 重建了历史源码，使字节码主体与链上一致，但元数据（含源码哈希）对不上。重建的源码作为单独的历史快照保存，没有覆盖当前源码。

### Etherscan：已提交，快照时仍在排队

8 个合约的源码都通过 <Term id="etherscan">Etherscan</Term> API V2（`chainid=11155111`）提交，都拿到了提交编号（GUID）。但到 **2026-11-12 15:39（新加坡时间）**，状态查询仍然是 `Pending in queue`，`getsourcecode` 仍显示未验证。**不能把它写成已经验证成功。** 代理关联（`verifyproxycontract`）返回成功，识别出实现是 V3，但注明 implementation saved (unverified - without ABI)，意思是实现地址已记下，但还没有经过验证的 <Term id="abi">ABI</Term>（合约的接口说明）。

拿到 GUID 只代表「已经排队」，不代表「已经通过」。

## V4：只在本地，没有上链

决策 D-04 在本地设计了 UBOX V4，用来修复 F-V3-001 和粉尘问题：

- <Term id="storage">存储</Term>兼容：`_scale` 仍在 slot 58，新变量 `_v4Initialized` 追加在 **slot 59**，不重排旧槽。
- `initializeV4()` 只执行一次，不重新铸币；<Term id="implementation">实现合约</Term>构造时锁定初始化。
- `type(uint256).max` 作为无限授权的哨兵：存储时不缩放，使用时不递减。
- 新增 `dustOf` 和 `sweepDust`：把不可见的粉尘挪到另一个地址，总供应不变。
- 测试：单元 **10/10** 通过；Fuzz **3/3 × 1000**（seed `0x5030`）通过；对最新 Sepolia 状态的 <Term id="fork">fork 模拟</Term>通过（部署约 2,777,602 gas，升级约 72,181 gas；升级后供应 100、A 99.99、B 0.01，粉尘为 0）。

<strong>V4 没有部署、没有<Term id="signature">签名</Term>、没有<Term id="broadcast">广播</Term>。</strong> Fork 模拟不产生真实交易，也没有交易哈希。快照时 UBOX 代理仍然指向 V3。

<Callout type="warn" title="修了一个问题，可能多了一个权力">

`sweepDust` 允许持有人本人，<strong>也允许代币 <Term id="owner">owner</Term></strong>，把某个账户的不可见粉尘转走。前者像用户处理自己的找零，后者像商家管理员把顾客的零头调到别的账户。这带来维护便利，也引出治理问题：管理员**应不应该**有这个权力？代码能做到，不代表业务上应该允许。

</Callout>

## 一条可重复的证据链

1. 找到地址和部署/升级交易，确认网络是 Sepolia（<Term id="chainid">chainId</Term> 11155111）。
2. 找到对应的编译参数、源文件和元数据，理解 exact match 和 match 的差别。
3. 读取代理当前的实现地址，不要把历史实现当成当前版本。
4. 对需要证明的状态变化，在目标区块附近核对交易、<Term id="event">事件</Term>和存储读取。
5. 记录来源、时间、区块高度、命令、结果和**不确定的地方**。

这一步就像检查 App 升级。不只看安装包版本，还要核对线上真正运行的版本、配置和迁移后的用户数据。

## Phase-0 的边界

- 公共 <Term id="rpc">RPC</Term> 没有 <Term id="archive-node">archive</Term> 数据，无法对升级前的历史区块做 fork。Phase-0 改为在本地重建升级路径，并如实注明：没有把没做的 fork 写成通过。
