<p class="lead">To read an Ethereum transaction on Etherscan, check its status, token transfers and event logs. In the Sepolia Counter example below, the call succeeded, no tokens moved, and the <code>Incremented</code> event recorded the counter rising to 1.</p>

<h2 id="inspect-a-transaction">Inspect a transaction without a wallet</h2>

Click the link below. This is the first `increment` transaction, which added one to the counter:

<Tx h="0x9e63d7a2bf89d4dd7330623a6729ce35f1c249c9d735de0e7fb770b380a98e73" />

The page opens the Sepolia block explorer. This transaction is in block **12110964**, and it also appears in the table below. You only need a browser. You need no wallet connection, faucet or account.

On the page, look for these three items from top to bottom. What you should see:

1. **Status** shows **Success**. The call completed.
2. **Tokens Transferred** is empty, or says none. Raising a counter does not move tokens. The sender still paid a network fee.
3. **Logs** record the `Incremented` event. If the explorer can decode the log, `newCount` is **1**. If you cannot see the field, do not guess. Decoding needs the interface description. Compare the code and the record below instead.

These numbers describe that one call. The historical snapshot’s `count()` of 2 comes after the later calls.

### Optional: read the same receipt in a terminal

If your computer has `curl`, copy this whole block. The recorded transaction hash is already filled in. This **does not sign or send a transaction** and needs no key:

```bash
curl -sS https://ethereum-sepolia-rpc.publicnode.com \
  -H 'Content-Type: application/json' \
  --data '{"jsonrpc":"2.0","id":1,"method":"eth_getTransactionReceipt","params":["0x9e63d7a2bf89d4dd7330623a6729ce35f1c249c9d735de0e7fb770b380a98e73"]}'
```

Look at `result.status` (`0x1` means success), `blockNumber` and `logs`. RPC block numbers are hexadecimal. The explorer displays decimal. If the result is `null` or the service returns an error, check the network. You can also try later. A failed lookup does not mean a failed transaction.

## What the contract does

Counter is a teaching contract written in <Term id="solidity">Solidity</Term>, only a dozen lines long:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Counter {
    uint256 public count;
    address public owner;
    event Incremented(address indexed by, uint256 newCount);

    constructor() { owner = msg.sender; }

    function increment() external {
        count += 1;
        emit Incremented(msg.sender, count);
    }

    function reset() external {
        require(msg.sender == owner, "not owner");
        count = 0;
    }
}
```

Anyone may call `increment`. It adds one and emits the `Incremented` <Term id="event">event</Term>. Only the <Term id="deploy">deployer</Term>, `owner`, may call `reset`. That sets the count to zero. It was <Term id="compile">compiled</Term> with solc (the Solidity compiler) 0.8.34.

## What the numbers teach

- **The chain keeps the books for you**: `count`, `owner` and the event logs all live on-chain. Changing state means paying <Term id="gas">gas</Term> yourself.
- **Deploying costs far more than calling**: deployment used 1,652,641 gas, reset only 23,626. Most of the cost is writing the contract's code into chain state. The few lines of arithmetic are cheap by comparison.
- **The same function can cost different gas**: the increment from 0 to 1 used 127,229 gas, from 1 to 2 only 29,309. Writing a <Term id="storage">storage slot</Term> from zero to non-zero is expensive. Changing an already non-zero value is much cheaper.
- **Confirmed <Term id="transaction">transactions</Term> are practically irreversible for beginners**: reset sets the number back to zero but cannot erase the earlier increment transactions or events. The history is still there. Rare network reorgs exist; for learning, treat a confirmed record as fixed.
- **This contract cannot gain features**: to add batch operations or upgradeability you must choose an <Term id="upgradeable">upgradeable</Term> pattern at deployment time. That is what UBOX does in Chapter 13.

## Everyday equivalent

Picture a public counter outside a shop. Every partner merchant can check it. Each call changes the count by one. If the count tracks raffle entries or completed public tasks, an on-chain counter reduces disputes. It stops one side from changing the number alone. It cannot prove that a real person ever stood at the counter.
