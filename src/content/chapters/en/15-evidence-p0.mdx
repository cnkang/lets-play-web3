## Test layers: each answers a different question

The tests used Foundry 1.9.0. The test framework generated the addresses. It did **not** use the local <Term id="private-key">private keys</Term>. No production contract logic was changed to make tests pass.

### Two instructive side stories

- **Fuzzing failed twice along the way**. The cause was the assertion order in the **test oracle**. The test oracle is the test code that computes the expected result. The test was fixed. **The contracts were not changed.** A failing test does not always mean a buggy contract. The test itself can be wrong.
- **16 unexpected Handler reverts**: in the invariant run, `batchTransferFrom` was called 3,166 times. The Handler is helper code in the test that fires random calls for you. Of those calls, 16 (about 0.5%) <Term id="revert">reverted</Term> in a way the Handler did not expect. The whole Handler call rolled back. The invariants still held. Phase-0 treated this as **residue in the test scaffolding (an oracle edge case)**, not a contract bug. The careful next step is a minimal reproduction. It would confirm that the reverts are an expected constraint.

<Callout type="warn" title="49/49 passing ≠ no vulnerabilities">

All unit tests passed and the review still recorded 1 Medium, 3 Low and 6 Info findings. Tests only prove that the cases you thought of behave.

</Callout>

## Source matching: Sourcify and Etherscan

What lives on-chain is <Term id="bytecode">bytecode</Term>, not source code. **Source verification** recompiles the source you submit with the same compiler settings. If the bytecode matches what is on-chain, the source is published and marked verified. (Appendix B explains how to get an Etherscan <Term id="api-key">API key</Term>.)

### Sourcify: all 8 addresses matched

<Term id="sourcify">Sourcify</Term> has two common results. **exact_match** means everything matches, including metadata. Metadata is the descriptive data the compiler appends to the bytecode. **match** means the bytecode matches but the metadata does not entirely. Of the 8 addresses, **5 are exact_match and 3 are match**. Do not call them all "exact".

Why only "match" for V1 and V2? Chapter 14 changed V1's source for V3. At that time the workspace **had no Git history**. The deployed version could not be retrieved. Phase-0 rebuilt the historical source. The main bytecode now matches the chain. The metadata does not. Metadata includes a hash of the source. The rebuilt source is kept as a separate historical snapshot. It did not overwrite the current files.

### Etherscan: submitted, still queued at the snapshot

All 8 contracts were submitted through the <Term id="etherscan">Etherscan</Term> API V2 (`chainid=11155111`). Each received a submission ID (GUID). But as of **2026-11-12 15:39 Singapore time**, the status check still returned `Pending in queue`. `getsourcecode` still showed them as unverified. **It must not be described as verified.** Linking the proxy (`verifyproxycontract`) returned success. It recognised V3 as the implementation. It also noted "implementation saved (unverified - without ABI)". The implementation address was recorded. There is no verified <Term id="abi">ABI</Term> (the contract's interface description) yet.

Receiving a GUID means "queued", not "passed".

## V4: local only, never on-chain

Decision D-04 designed a UBOX V4 locally to fix F-V3-001 and the dust issues:

- <Term id="storage">Storage</Term>-compatible: `_scale` stays in slot 58 and the new `_v4Initialized` is appended in **slot 59**, without reordering old slots.
- `initializeV4()` runs only once and does not mint again. The <Term id="implementation">implementation</Term> locks initialisation in its constructor.
- `type(uint256).max` becomes an infinite-allowance sentinel: stored without scaling and never decremented when used.
- New `dustOf` and `sweepDust` move invisible dust to another address without changing total supply.
- Tests: unit **10/10** pass. Fuzz **3/3 × 1000** (seed `0x5030`) pass. A <Term id="fork">fork simulation</Term> against the latest Sepolia state passed (deploy about 2,777,602 gas, upgrade about 72,181 gas). After the upgrade, supply was 100, A 99.99, B 0.01, with zero dust.

**V4 was not deployed, <Term id="signature">signed</Term> or <Term id="broadcast">broadcast</Term>.** A fork simulation produces no real transaction and no transaction hash. At the snapshot the UBOX proxy still pointed to V3.

<Callout type="warn" title="Fixing one problem can add a new power">

`sweepDust` lets the holder, **and also the token <Term id="owner">owner</Term>**, move an account's invisible dust. The first is like a customer tidying up their own small change. The second is like a shop admin moving a customer's change into another account. It is convenient for maintenance. It also raises a governance question: **should** the admin have this power at all? Being able to do something in code does not mean the business should allow it.

</Callout>

## A repeatable chain of evidence

1. Find the address and its deployment/upgrade transactions. Confirm the network is Sepolia (<Term id="chainid">chainId</Term> 11155111).
2. Find the matching compiler settings, source files and metadata. Understand the difference between exact match and match.
3. Read the proxy's current implementation address. Do not mistake a historical implementation for the current one.
4. For any state change you want to prove, check transactions, <Term id="event">events</Term> and storage reads around the relevant block.
5. Record the source, time, block height, commands, results and **anything uncertain**.

It is like checking an app upgrade. Look at the installer version. Also look at what really runs in production, its configuration and the migrated user data.

## Limits of Phase-0

- The public <Term id="rpc">RPC</Term> has no <Term id="archive-node">archive</Term> data. Pre-upgrade blocks could not be forked. Phase-0 rebuilt the upgrade path locally instead. It said so plainly. It did not report an unperformed fork as passing.
- The static analyser Slither (a tool that scans source code for common problems without running it) was not run (not installed, optional).
- The next round only needs to track D-02's final result and reproduce the 16 Handler reverts, rather than extending Phase-0 forever.
