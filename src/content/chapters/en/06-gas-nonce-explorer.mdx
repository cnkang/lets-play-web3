## Gas: the metering fee for execution

**Gas** is the unit that measures the work the <Term id="evm">EVM</Term> does. Think of posting a parcel. The price depends on whether you send it. It also depends on handling cost and how busy things are.

Under the <Term id="eip-1559">EIP-1559</Term> fee market:

- fee paid = `gasUsed × effective gas price`
- effective gas price ≈ `base fee + tip`
- **`gasUsed × base fee` is burned** (removed from circulation, credited to nobody). **`gasUsed × tip` goes to the <Term id="validator">validator</Term>** that includes the block.

Which part is larger depends on the <Term id="base-fee">base fee</Term> and <Term id="tip">tip</Term> at the time. There is no fixed ratio. Check it against the five real Counter transactions from the lab (all values in <Term id="wei">wei</Term>):

</T>

Sepolia was quiet then. The base fee was only around 20 wei. The default tip was 50 wei. In the first three transactions, **the tip was the larger part**. About 71% of the deployment fee went to the validator. Only after the tip was cut to 1 wei did the burned part dominate again. The same 127,229-gas increment cost 8,651,572 wei with a 50 wei tip. It cost 2,671,809 wei with a 1 wei tip. The difference is the tip, not the computation.

<Callout type="warn" title="Failed transactions cost money too">

A failed transaction is still a transaction. It uses a nonce, consumes gas and appears in the explorer. Only its state changes are <Term id="revert">rolled back</Term>. Chapter 12 has a deliberately failing transaction that used 51,719 gas. However high you set the <Term id="gas-limit">gas limit</Term>, the unused part is not charged. You pay only `gasUsed × effective gas price`.

</Callout>

## Nonce: the account's transaction counter

For an ordinary <Term id="eoa">externally owned account</Term>, the **nonce** is the sequence number of the account's transactions. It starts at 0. It goes up by one for every transaction included in a block. It orders transactions and prevents the same one from being replayed.

At the snapshot, **account A's nonce was 20**. A had sent 20 transactions included in blocks, using nonces 0 through 19. Its next transaction would use nonce 20. The nonce is **not** "a balance of 20". It is also not "20 successful calls". Nonce 15 was a deliberately failing transaction, and it still used up a nonce. Account B's nonce was 3 (nonces 0, 1 and 2 used).

## A real lesson about a "stuck" transaction

A lower tip makes a transaction more likely to wait at the back of the queue when the network is busy. The lab practised this on purpose:

- **Nonce 3**: an increment with a tip of only **1 wei**. The chain was not busy, so it was still mined: <Tx h="0xd61e57686959b7c4c9d774a6aa35b0fb9dac72e8317055146da4676a9e4e4b31" short /> (block 12111091).
- **Nonce 4**: the replacement script `replace-stuck.mjs` was designed to first send a 1 wei tip transaction at nonce 4 that would be hard to mine, and to watch it. If it was still waiting in the pending queue (the <Term id="mempool">mempool</Term>), it would send a replacement with **the same nonce and a higher tip (2 wei)**. The transaction mined at nonce 4 matches that script exactly (gas limit 140,000, tip 2 wei): <Tx h="0x8141d5f30dc7abd76c7c2ebfcc9f4861af625e38ca11220605057e1275512da8" short /> (block 12111181).

**Only the transaction that was finally mined is visible on-chain.** This book does not count a pending transaction as an on-chain result. A wallet or script can compute a <Term id="tx-hash">hash</Term> before broadcasting, so an ID alone proves neither successful broadcast nor inclusion in a block. Check its receipt and block number.

<Callout type="note" title="Why can the same nonce replace a transaction?">

Only one transaction per account per nonce can ever be mined. Nodes usually accept a new transaction with the same nonce and a higher fee. The new one replaces the old transaction waiting in the mempool. Once one of them is in a block, the other is void forever.

</Callout>

## What to look at in a block explorer

(See Figure 2 in Chapter 5 for the whole flow.)

1. **Network**: make sure it is Sepolia (the address bar reads `sepolia.etherscan.io`). Do not confuse <Term id="testnet">testnet</Term> and <Term id="mainnet">mainnet</Term>.
2. **Status**: success or failure. A failed transaction may still have consumed gas.
3. **From / To**: who sent it and which account or contract it went to.
4. **Method / Logs**: which function was called and which <Term id="event">events</Term> were emitted. An event is not always the final state of an asset. Chapters 11–12 show an event with a net change of zero.
5. **Block / Transaction Hash**: the block that contains it and its unique identifier.

Judge the on-chain result by **status, events and balance changes together**, never just because a program or bot says "success".
