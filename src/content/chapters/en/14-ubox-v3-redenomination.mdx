<p class="lead">"Knock four zeros off" as a contract upgrade: you can change the bookkeeping from now on, but not the <Term id="event">logs</Term> already written into history.</p>

## Goal and difficulty

V3's job: make **10,000 old UBOX = 1 new UBOX**.

The <Term id="erc20">ERC-20</Term> standard lets you ask "How many tokens does this address hold?" It does not require a way to ask "Which addresses hold tokens?" Updating only A and B could miss another holder. One rule must hold before and after the conversion: the balances must add up to the total supply. A rule like that is called an <Term id="invariant">invariant</Term>.

## Design: a global scale

- **Raw balances stay stored in old units**; no <Term id="storage">storage</Term> is rewritten.
- A new global factor `scale = 10000` lives in **slot 58**, after the existing `__gap` (slots 8-57), without reordering any old slot.
- `balanceOf` / `totalSupply` / `allowance` return "raw value ÷ 10,000".
- `transfer` / `approve` / `burn` and V2's batch functions all work in **new units**: passing 1e18 means one new token, and 10,000 times as many raw units are moved.
- **`decimals()` (the number of <Term id="decimals">decimal places</Term>) stays 18.** Reading `balanceOf()` directly shows the new number.

An alternative: change `decimals()` to 22. <Term id="wallet">Wallets</Term> would also display amounts 10,000 times smaller, but `balanceOf()` would still return the old raw number. The goal here was for `balanceOf()` itself to show the new figure, so that approach was not chosen.

## A one-time initializeV3

- V1's `initialize()` had already set `_initialized` to 1, and V1 does not use <Term id="openzeppelin">OpenZeppelin</Term>'s `Initializable`, so this is not `reinitializer(2)`: it checks `_scale == 0` and then writes `_scale = 10000`.
- It **must not** call V1's `initialize` again, and it neither <Term id="mint">mints</Term> nor transfers.
- The V3 implementation's <Term id="constructor">constructor</Term> locks `_scale` in **the <Term id="implementation">implementation</Term>'s own storage**, so nobody can initialise the implementation directly.
- So that V3 could override getters such as `balanceOf`, the V1 **source** turned the original public variables into internal variables in the same slots plus virtual functions. That changes neither the <Term id="storage-layout">storage layout</Term> nor the already-deployed V1/V2 <Term id="bytecode">bytecode</Term>. It does mean the current source no longer reproduces the historical V1/V2 exactly (Chapter 15 shows the consequence).

Worked example: A's raw balance 999,900e18 ÷ 10,000 = 99.99e18. And 99.99 + 0.01 = 100.

The simulation also tried "A sends 1 new UBOX to B" (which would give A 98.99, B 1.01, supply still 100). **That demo transfer was never authorised for <Term id="broadcast">broadcast</Term>** and does not exist on-chain.

## Historical events are not rewritten

Keep this in mind:

- The `Transfer` log for "100 to B" in Chapter 12's successful batch records **100e18 in old units**.
- After the redenomination, B's `balanceOf` is **0.01**.
- Anyone who reads that old log **as new units** will think B received 100: **10,000 times too much**.

A <Term id="redenomination">redenomination</Term> changes the bookkeeping and the unit of new events **from now on**. It cannot rewrite logs already on-chain, and it cannot set any market price. When reading historical data, convert separately on each side of the upgrade.

## Dust and findings

- **Dust**: raw balances that are not multiples of 10,000 are truncated for display, so they look like 0 yet cannot be moved (recorded in Phase-0 as Low findings F-V3-002 and F-V3-003). **At the snapshot every known holder's raw balance was divisible by 10,000**, so this does not affect current holders.
- **Medium finding F-V3-001**: `approve(spender, type(uint256).max)` <Term id="revert">reverts</Term> with `"amount overflow"` because `value × 10000` overflows (exceeds the largest value that number type can hold); V3 has no "infinite <Term id="allowance">allowance</Term>" sentinel (a special number meaning "no limit"). Many protocols rely on max approvals, so **do not plug UBOX into a protocol that depends on max approve**. It is a compatibility and numeric-boundary issue, not damaged assets; at the snapshot all UBOX allowances on-chain were 0.

<Callout type="note" title="Everyday analogy: converting points">

A shop stores loyalty points in a tiny base unit and the app shows them divided by 10,000. If the underlying balance is not a multiple of 10,000, the app hides a small remainder: that is dust. When a payment service tries to set the industry-standard "unlimited standing approval", the internal conversion overflows at the maximum value and the integration fails: that is F-V3-001.

</Callout>

<Callout type="warn" title="One more time">

V1's `initialize` was **not** called during the V3 upgrade and **must never** be called again. Every upgrade is a public transaction with a hash, events and an implementation-slot change, and the old V2 bytecode is still at its original address.

</Callout>
